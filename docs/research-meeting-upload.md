# Research: технологическая реализация загрузки записей встреч

**Контекст:** [PRD](./prd-meeting-recording-upload-and-display.md), [План реализации](./plan-meeting-recording-upload-and-display.md)
**Дата**: 2026-08-02

Цель документа — выбрать конкретные технические решения для трёх фаз плана (приём файла, хранение, интеграция с обработкой, отдача на фронтенд), исходя из того, что уже есть в репозитории, а не абстрактно.

## Что уже есть в проекте (ограничивает выбор)

- NestJS 11 на `@nestjs/platform-express` (не Fastify) — значит инструменты для загрузки файлов должны быть express/multer-совместимыми.
- Персистентность везде in-memory (`MeetingsRepository`, `UsersRepository`) — нет ни БД, ни объектного хранилища, ни очереди в зависимостях (`apps/api/package.json` — только `@nestjs/*`, `class-validator`, `rxjs`).
- Нет Docker/`.env`/инфраструктурных файлов в репозитории — деплой-цель пока не зафиксирована, разработка идёт локально.
- PRD прямо ограничивает скоуп: загрузка одним запросом без чанкинга/докачки, лимит размера и форматов фиксируется явно, хранилище метаданных отделено от бинарного хранилища.
- `apps/api/CLAUDE.md` фиксирует паттерн: там, где реальной внешней системы ещё нет (например, выдача токенов в `AuthService.generateToken`), в код закладывается **шов** (seam) — простая реализация сейчас, явная точка замены потом. Это стоит повторить для очереди обработки в Фазе 2.

## 1. Приём файла (multipart/form-data) в NestJS

`@nestjs/platform-express` даёт готовую интеграцию с [multer](https://github.com/expressjs/multer) через `FileInterceptor('file')`. Это стандартный и единственный реалистичный вариант при Express-платформе (аналог на Fastify — `@fastify/multipart`, но платформа уже выбрана).

Ключевое решение — **storage engine** multer:

| Вариант           | Поведение                             | Проблема для этого проекта                                                                                                         |
| ----------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `memoryStorage()` | Буферизует весь файл в `Buffer` в RAM | Видео/аудио файлы (десятки–сотни МБ) в памяти на каждый параллельный запрос — риск OOM ещё до того, как дошли до валидации размера |
| `diskStorage()`   | Стримит файл на диск по мере приёма   | Требует своего пути хранения, но не держит файл в памяти — подходит                                                                |

**Рекомендация:** `diskStorage`, запись во временную директорию (`storage/tmp`), финальное перемещение в постоянное расположение только после успешной валидации. Это также прямо ложится на требование задачи "отклонение без сохранения файла" — при провале валидации удаляется временный файл, а не тот, что уже числится как запись встречи.

**Лимит размера — на уровне multer, а не только в бизнес-логике:**

```ts
MulterModule.register({ limits: { fileSize: MAX_RECORDING_SIZE_BYTES } });
```

Превышение лимита обрывает приём потока на уровне multer (файл не дописывается целиком), это дешевле, чем сначала сохранить весь файл и потом отклонить.

## 2. Валидация формата — почему одного `mimetype` недостаточно

Клиент присылает `mimetype` из заголовка `Content-Type` части формы — это то, что сообщил браузер/клиент, а не то, что реально лежит в файле. Его легко подделать (переименовать `.exe` в `.mp4`). Для эндпоинта, который потом кладёт файл во внешний пайплайн обработки, это стоит закрыть на двух уровнях:

1. **Быстрый отсев** — `multer` `fileFilter` по `mimetype`/расширению, ещё до записи на диск (дёшево, отсекает очевидный мусор).
2. **Проверка по содержимому (magic bytes)** — после приёма файла, до перемещения в постоянное хранилище и до создания записи в репозитории. NestJS 10+ даёт для этого встроенный `ParseFilePipe` с `FileTypeValidator` (сниффинг по сигнатуре файла), применяется как pipe к параметру `@UploadedFile()`.

Если нужен более гибкий сниффинг, чем встроенный `FileTypeValidator`, есть пакет [`file-type`](https://github.com/sindresorhus/file-type) — но начиная с v17 он **чисто ESM**, а `apps/api` компилируется как CommonJS (`tsconfig.json`: `module: nodenext` без `"type": "module"` в `package.json`) → потребует `await import('file-type')` (динамический импорт), а не обычный `import`. Стоит сначала попробовать встроенный `FileTypeValidator` — его, вероятно, достаточно и он не тянет эту сложность.

**Порядок проверок в `POST /meetings/:id/recordings`:**

1. `AuthGuard` (уже есть) → `req.user.id`.
2. Проверка владения встречей (`findByIdAndOwner`) — до того, как файл целиком принят (см. пункт 5).
3. `multer` `fileFilter` + `limits.fileSize` — быстрый отсев на уровне приёма.
4. `ParseFilePipe([MaxFileSizeValidator, FileTypeValidator])` — проверка уже принятого файла по содержимому.
5. Только после (3) и (4) — перемещение файла из tmp в постоянное расположение, создание записи в репозитории со статусом «Загружено».

## 3. Где хранить бинарные данные

| Вариант                                      | Плюсы                                                                                                                                            | Минусы                                                                                                                            | Готовность в проекте                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| In-memory (как `MeetingsRepository`)         | Ничего внедрять не нужно                                                                                                                         | Теряется при рестарте процесса, распухает RAM пропорционально суммарному размеру файлов — непригодно для бинарей от нескольких МБ | Уже есть, но не подходит                             |
| Локальная файловая система хоста API         | Ничего нового не внедряется, просто реализовать, укладывается в размер Фазы 1                                                                    | Не переживает горизонтальное масштабирование (файл лежит на конкретном инстансе), без бэкапа — потеря диска = потеря записей      | Ничего не требует                                    |
| Объектное хранилище (S3 / self-hosted MinIO) | Масштабируется, отделено от процесса API, стандарт для медиафайлов, в будущем даёт presigned URL для прямой загрузки с браузера мимо API-сервера | Новая внешняя зависимость и конфигурация (креды, бакет, SDK) — сейчас в репозитории нет вообще никакого внешнего сервиса/`.env`   | Требует инфраструктурного решения, которого пока нет |

**Рекомендация для Фазы 1:** локальная файловая система за отдельной абстракцией хранения (`RecordingsStorage`/аналог, соседний по духу с тем, как `MeetingsRepository` уже отделяет доступ к данным встречи от контроллера). Файл пишется под `apps/api/storage/recordings/<meetingId>/<uuid>.<ext>`, а в (пока тоже in-memory) `RecordingsRepository` хранится только путь + метаданные — это прямо то, что описывает задача 1 плана и техническое ограничение PRD «хранилище метаданных должно быть отделено от бинарного хранения». Абстракция хранения — это тот же шов, что и `AuthService.generateToken`: сейчас простая реализация (диск), но контроллер/сервис не завязаны на неё напрямую, и подмена на S3/MinIO позже не требует переписывать бизнес-логику.

**Важно зафиксировать сразу:** имя файла на диске — **всегда** серверный UUID, никогда не оригинальное имя от пользователя (path traversal, коллизии, спецсимволы). Оригинальное имя файла хранится только как метаданные для отображения в списке.

Отметить явно как известное ограничение: локальный диск не годится, если/когда появится деплой на несколько инстансов API — это следующий шаг, не блокер для текущего плана.

## 4. Проверка владения — до приёма файла, а не после

`MeetingsController.findOne` проверяет владение и отдаёт 404 без утечки существования встречи. Для загрузки файла тот же паттерн важен вдвойне: если проверять владение **внутри** обработчика после того, как `FileInterceptor` уже принял и записал весь файл на диск, чужой/неавторизованный запрос успевает потратить диск и трафик впустую ещё до 404.

Guards в NestJS выполняются раньше interceptor'ов на одном хендлере — поэтому имеет смысл вынести проверку владения встречей в отдельный guard (например, `MeetingOwnerGuard`, читающий `:id` из параметров маршрута), выполняющийся до `FileInterceptor`. Тогда неавторизованный запрос получает 404 до того, как multer начинает писать файл на диск.

## 5. Интеграция с обработкой (Фаза 2)

PRD прямо выносит саму обработку за скоуп — нужна только точка постановки в очередь и метод обновления статуса, которым пользуется внешний процесс. В репозитории сейчас нет ни очереди, ни message broker'а, ни реального внешнего сервиса.

**Постановка в очередь:** завести интерфейс-порт, а не тянуть Redis/BullMQ ради Фазы 2:

```ts
interface RecordingProcessingQueue {
  enqueue(recordingId: string): Promise<void>;
}
```

Реализация-заглушка на старте (в духе `AuthService.generateToken` — минимальная реализация с явным швом для замены). Когда появится реальный внешний пайплайн, естественная замена — `BullMQ` + Redis (`@nestjs/bullmq`), это стандартный выбор в экосистеме Nest для очередей с ретраями/backoff; но заводить эту зависимость сейчас — избыточно для того, что требует план.

**Обновление статуса «внешним процессом»** — тут есть развилка, которую стоит явно решить, а не выбрать по умолчанию:

- _Прямой вызов метода сервиса/репозитория_ (`RecordingsService.updateStatus(id, status)`), который пока вызывается только из тестов как имитация внешнего вызова — соответствует формулировке задачи Фазы 2 «изменение статуса... смоделированное в тесте как внешнее». Не требует HTTP-поверхности вообще.
- _Отдельный HTTP webhook_ (`PATCH /internal/recordings/:id/status`), который сможет дёргать реальный внешний сервис, когда он появится — потребует отдельной аутентификации (не `AuthGuard` пользователя, а сервисный секрет/подпись), это выходит за рамки того, что описывает план Фазы 2.

**Рекомендация:** в Фазе 2 реализовать только прямой метод на уровне сервиса/репозитория — это ровно то, что покрывают формулировки задач и критерии готовности плана. HTTP webhook с сервисной аутентификацией — заметка на будущее, когда появится реальный внешний пайплайн, не часть текущего плана.

## 6. Frontend: загрузка с прогрессом (Фаза 3)

`fetch` не даёт надёжного кросс-браузерного способа отслеживать прогресс отправки тела запроса (upload progress events через `ReadableStream` в `fetch` поддерживаются не везде одинаково, Safari — исторически проблемное место). `XMLHttpRequest` с `xhr.upload.onprogress` — более скучный, но предсказуемо рабочий вариант для индикации прогресса, которую требует и PRD, и задача плана. Стоит обернуть в небольшой хелпер, а не тянуть библиотеку.

Клиентская проверка формата/размера — только UX-подсказка (мгновенная обратная связь до сетевого запроса), сервер остаётся источником истины; это и требует техническое ограничение PRD («должны проверяться и на клиенте, и на сервере»).

**Момент, требующий отдельного решения продукта, а не чисто технического:** формулировка задачи плана — «повторная загрузка списка записей при открытии страницы» (просто рефетч при маунте), а сценарий PRD — «пользователь обновляет страницу... видит актуальный статус... **без ручных действий**». Простой рефетч на открытие не даёт «без ручных действий», если пользователь не обновляет вкладку сам. Лёгкий поллинг (например, каждые N секунд, только пока в списке есть запись со статусом «В обработке», с остановкой после «Готово»/«Ошибка») ближе к формулировке PRD, но это уже за пределами буквального текста задачи плана. Стоит явно решить с продуктовой стороны, входит ли поллинг в Фазу 3 или сценарий PRD трактуется как приемлемый через ручной рефреш браузера — сейчас это разночтение между двумя документами, а не техническое ограничение.

## 7. Безопасность — что стоит закрыть в рамках этого плана

- Имя файла на диске — только серверный UUID (см. п. 3), не пользовательский ввод.
- Директория хранения — вне статики, которую Express может отдать напрямую (не через `express.static`), доступ к бинарнику только через авторизованный API-путь, если он вообще понадобится (в скоупе PRD скачивание не предусмотрено — «Не в скоупе»).
- Сканирование на вредоносное содержимое — сознательно не в скоупе этого плана (PRD его не требует), но стоит зафиксировать как известный пробел для будущего продакшен-деплоя, если запись будет открыта внешним пользователям.

## 8. Тестирование

E2E-тесты уже используют `supertest` (`test/meetings.e2e-spec.ts`) — для загрузки файлов тот же инструмент поддерживает `.attach(fieldName, buffer, filename)`, не требует отдельной библиотеки. Тестовые файлы (валидный формат, невалидный формат, превышение размера) можно генерировать в памяти (`Buffer.alloc(...)`) в самом тесте вместо коммита бинарных фикстур в репозиторий — короче и не раздувает репозиторий бинарями.

## Итог по фазам

| Фаза | Ключевое решение                                                                                                                                                                                                                                                                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `FileInterceptor` + `diskStorage` (не memory) → tmp-директория → `ParseFilePipe`(`MaxFileSizeValidator`, `FileTypeValidator`) → перемещение в постоянное хранилище только после валидации; отдельный `RecordingsStorage` за интерфейсом на локальном диске; UUID-имена файлов; проверка владения встречей до приёма файла (guard, а не логика внутри хендлера) |
| 2    | `RecordingProcessingQueue`-порт с простой заглушкой (шов для BullMQ/др. позже); обновление статуса — прямой метод сервиса, без HTTP webhook на этом этапе                                                                                                                                                                                                      |
| 3    | `XMLHttpRequest` для прогресса загрузки (не `fetch`); клиентская валидация — только UX-слой; решить отдельно с продуктом, нужен ли лёгкий поллинг статуса вместо чистого рефетча на маунте                                                                                                                                                                     |
