# Plan: Meeting Recording Upload and Display

**PRD:** [docs/prd-meeting-recording-upload-and-display.md](./prd-meeting-recording-upload-and-display.md)
**Дата**: 2026-07-31

## Фазы реализации

### Фаза 1: Backend — загрузка и хранение записей

**Цель:** Минимальный рабочий путь (tracer bullet) — запись встречи можно загрузить, сохранить и получить обратно списком через API, с валидацией и проверкой владения встречей.
**Затрагивает:** backend
**Задачи:**

- [ ] Модуль `recordings`: сущность (id, meetingId, filename, size, format, status, uploadedAt) + репозиторий по аналогии с `MeetingsRepository`
- [ ] `POST /meetings/:id/recordings` — загрузка файла, привязка к встрече, сохранение метаданных и бинарных данных, статус по умолчанию «Загружено»
- [ ] Валидация загружаемого файла: допустимые аудио/видео форматы и максимальный размер, отклонение с понятной ошибкой (400) без сохранения файла
- [ ] `GET /meetings/:id/recordings` — список записей встречи; доступ только владельцу встречи (404 при чужой/несуществующей встрече, без утечки существования, аналогично `GET /meetings/:id`)
- [ ] e2e-тесты: успешная загрузка и появление в списке, несколько файлов на встречу, отклонение неверного формата, отклонение превышения размера, изоляция по владельцу

**Когда готова:** Все e2e-тесты из списка задач проходят; через API можно загрузить несколько файлов к встрече и получить их списком со статусом «Загружено», доступ ограничен владельцем встречи.

### Фаза 2: Backend — интеграция с обработкой

**Цель:** Загруженный файл передаётся во внешний пайплайн обработки, а его статус может обновляться независимо от загрузки и корректно отдаётся через API.
**Затрагивает:** backend
**Задачи:**

- [ ] Точка интеграции с обработкой (сервис/интерфейс постановки в очередь), вызываемая после сохранения файла
- [ ] Вызов постановки в очередь сразу после успешной загрузки в `POST /meetings/:id/recordings`
- [ ] Метод обновления статуса записи в репозитории/сервисе — точка, которой пользуется внешний процесс обработки
- [ ] `GET /meetings/:id/recordings` всегда возвращает актуальное значение статуса из хранилища
- [ ] Тесты: постановка в очередь вызывается при загрузке; обновлённый статус корректно отражается в ответе GET

**Когда готова:** Тесты подтверждают, что успешная загрузка ставит файл в очередь обработки и что изменение статуса записи (смоделированное в тесте как внешнее) видно в `GET /meetings/:id/recordings`.

### Фаза 3: Frontend — страница встречи с загрузкой и списком записей

**Цель:** Пользователь может загрузить запись и увидеть список записей встречи со статусами прямо на странице встречи.
**Затрагивает:** frontend
**Задачи:**

- [ ] Страница `/meetings/[id]` в `apps/web`: загрузка данных встречи через `GET /meetings/:id`, обработка «встреча не найдена / не моя» (404)
- [ ] Блок загрузки файла: выбор файла, отправка в `POST /meetings/:id/recordings`, индикация прогресса/результата, отображение ошибок валидации (формат/размер) от API
- [ ] Список записей встречи: имя файла, дата загрузки, статус («Загружено» / «В обработке» / «Готово» / «Ошибка»), обновление списка после успешной загрузки
- [ ] Повторная загрузка списка записей при открытии страницы, чтобы отображался актуальный статус, выставленный внешней обработкой

**Когда готова:** На странице встречи пользователь загружает один или несколько файлов записи, видит их в списке с актуальным статусом; загрузка неверного формата/размера показывает понятную ошибку; открытие чужой встречи не показывает её записи.
